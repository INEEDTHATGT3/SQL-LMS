A plain GROUP BY silently omits any day with zero events, so a line chart develops tooth-shaped gaps and week-over-week math compares Tuesday against Thursday. The calendar spine — every desired bucket generated up front, then LEFT JOINed to the facts — guarantees an aligned, gap-free series where a zero is a real zero.

ALEFT preserves every calendar row even when events has none for it
BIt is faster by definition
CEvents has no primary key
DRIGHT JOIN is faster
Driving from the calendar keeps a row for every bucket — LEFT JOIN never drops calendar days that had zero events.

AA single date
BOne timestamp per day across the range
CAll orders from 2024
DA calendar view
generate_series yields one row per step of the range — a bucket spine you can join. Swap the interval to '1 month' to get month-start buckets.

Aligned Periods — WoW / MoM / YoY

Weekly Aligned Deltas

week-over-week
WITH daily AS (
  SELECT ts::date AS day,
         SUM(amount) AS revenue
  FROM orders
  GROUP BY ts::date
)
SELECT day,
       revenue,
       LAG(revenue, 7) OVER (ORDER BY day) AS prev_week_revenue,
       ROUND(100.0 * (revenue - LAG(revenue, 7) OVER (ORDER BY day))
             / NULLIF(LAG(revenue, 7) OVER (ORDER BY day), 0), 2) AS wow_pct
FROM daily
ORDER BY day;

Retention Curves & Churn

Cohort × Period Retention with Guards

retention matrix
WITH first_orders AS (
  SELECT user_id, MIN(order_date)::date AS first_day
  FROM orders
  GROUP BY user_id
),
mat AS (
  SELECT f.first_day AS cohort,
         o.order_date::date AS order_day,
         COUNT(DISTINCT o.user_id) AS retained
  FROM first_orders f
  JOIN orders o USING (user_id)
  GROUP BY 1, 2
)
SELECT m.cohort,
       m.order_day,
       m.retained,
       ROUND(100.0 * m.retained /
             (SELECT COUNT(*) FROM first_orders WHERE first_day = m.cohort), 2) AS pct
FROM mat m
ORDER BY 1, 2;

-- cohort size = scalar subquery counting users whose first_day matches

The planner computes MIN(order_date) per user (HashAggregate), merges back to orders, and group-aggregates by (cohort, order_day). When user_id is already the leading sort key, PostgreSQL can use an Incremental Sort on (first_day, order_day) — a favoured shape for daily retention jobs that stream through one ordered feed.

CThe total order count
DA window COUNT(*)
The scalar subquery counts users whose MIN(order_date) matches the cohort — the acquisition size of that first-month bucket.

BCOALESCE(retained, 1)
CIGNORE NULLS
DA CASE for negative pct
NULLIF(denom, 0) turns a missing or empty cohort into NULL so ROUND returns NULL instead of a divide-by-zero error.

Funnel Analysis at Depth

One Path, Ranked Steps, Timing

deep funnel with timing
WITH ranked AS (
  SELECT user_id, event, ts,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY ts) AS rn,
         MAX(CASE WHEN event = 'purchase' THEN ts END)
           OVER (PARTITION BY user_id) AS bought_at
  FROM events
  WHERE event IN ('view', 'cart', 'checkout', 'purchase')
)
SELECT event,
       COUNT(DISTINCT user_id) AS users
FROM ranked
GROUP BY event;

-- rn ranks each user's own funnel path; bought_at flags the deepest step's time
-- MySQL 8.0: same window shape

For step-to-step timing (how long between cart and checkout), correlate each step with the next event's timestamp — a LATERAL (SELECT ts FROM events e2 WHERE e2.user_id = r.user_id AND e2.rn = r.rn + 1) — or simply take LEAD(ts) inside the same ranking window. Funnel depth is strictly within a single user path.

Funnel ≠ retention. A funnel measures depth along one user's ordered journey (view → cart → purchase). Retention measures survival across periods, by cohort. Mixing the two vocabularies is the most common BI reporting error.
Funnel vs retention — which distinction is right?
AFunnel is per-path step depth; retention is per-cohort survival across periods
BThey are synonyms
CRetention is a funnel with one step
DFunnels need timestamps only
Funnel = how deep one user got in a single journey; retention = how many of a cohort are still active in later periods.

Approximate Analytics at Scale

HyperLogLog, MySQL APPROX_COUNT_DISTINCT, Sampling

Exact COUNT(DISTINCT) keeps the full set of seen values in memory — O(distinct), growing per row. HyperLogLog (HLL) instead folds values into a fixed-size register array and returns an estimate with a bounded error (~1%). That is precisely the contract a high-cardinality dashboard needs: constant memory, near-exact counts.

postgres hll
CREATE EXTENSION IF NOT EXISTS hll;

SELECT hll_cardinality(hll_add_agg(hll_hash_integer(user_id))) AS approx_users
FROM events;

Why does HLL beat exact DISTINCT on high cardinality?
AIt is exact at low cardinality only
BFixed memory budget regardless of distinct count
CIt compresses the output table instead
DIt stores sampled rows to disk
HLL keeps a fixed register array (e.g. ~16 KB) and never stores the values themselves — memory is constant while exact DISTINCT grows with the distinct count.

RE-READ BEFORE ANY INTERVIEW / CONTEST

  • Calendar spine: generate_series / recursive CTE keeps every bucket; LEFT JOIN makes zeros visible
  • Aligned-period LAG: a dense daily series makes LAG(x, 7) a true week-ago; bucket weeks before comparing

Glossary

calendar tableA generated spine of every desired time bucket (generate_series / recursive CTE) used to keep zero-activity periods visible.
aligned periodComparing the same weekday/period of a previous cycle (WoW/MoM/YoY) so like compares with like.
retention cohortUsers grouped by first-activity period; retention = survivors in later periods divided by cohort size.
churnThe complement of retention: users lost between periods; chased with cohort curves.
funnelAn ordered step sequence counted per user along one path, ranked with ROW_NUMBER.
HyperLogLogProbabilistic cardinality sketch with fixed memory and ~1% error for COUNT DISTINCT at scale.
approximate aggregateAn aggregate that trades a tiny bounded error for constant memory (HLL, APPROX_COUNT_DISTINCT, sampling).
