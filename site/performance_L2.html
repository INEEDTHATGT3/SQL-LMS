Join Algorithms — When the Planner Picks What

The optimizer is a cost calculator with an uncertain view of your data. Performance work is teaching it: better statistics, better index options, better habits.

Every join carries two competing costs. Startup cost is what it takes before the first row is emitted — building a hash table, sorting an input. Total/per-tuple cost is what each extra row adds over the whole job. Hash join pays setup once (build the hash), then probes every outer row cheaply — the win when both inputs are large and the hash table fits in work_mem. Nested loop pays almost no setup but rescans the inner side for every outer row, so it is only cheap when the outer input is small and the inner is an index probe. Merge join demands sorted inputs, so the query pays a sort (or an already-sorted index scan) up front; it wins on equality-heavy joins where the ordering exists, or where you want sorted output anyway. 'How the planner joins' is really 'which algorithm minimizes estimated total cost for inputs of this estimated size' — and those sizes come from statistics, so stale stats change the join verdict. Read the shape of a plan with EXPLAIN (costs off); the node order and the presence of Hash/Sort nodes tell you more than the numbers.

join algorithms in EXPLAIN
-- Nested Loop: outer rows × index probe
EXPLAIN SELECT * FROM small s JOIN big b ON s.id = b.sid;

Statistics & ANALYZE — Teaching the Planner

How Planner Estimates Selectivity

Planner uses: histogram (most common values), n_distinct, null_frac, correlation. For range: histogram bounds + linear interpolation. For equality: MCV list + 1/n_distinct for non-MCV. For correlated columns: independence assumption (wrong) unless extended stats exist. These numbers ARE the cost model — they pick join order, join method, and index-vs-seq-scan. Stale statistics → wrong cardinality → wrong plan.

Problem Set — L2 Drills

  • L2
    Hash vs Nested-Loop Decision
    drill · join-algorithm
    Query joins large_table (1M rows) with small_table (100 rows) on id. Which algorithm should the planner pick, and why — in cost terms? What gets built, how many times is the other side read, and what changes if work_mem is tiny?
    Hash Join: build a hash on the 100-row side, probe once per large row — ~1M probes, no rescan
    Nested Loop would rescan the inner for every outer row, so the 100-row side must be inner
    If the hash table exceeds work_mem it spills to disk — re-order inputs or raise work_mem
  • L2
    Composite Index for Multi-Column Query
    drill · composite-index
    Query: WHERE user_id = 123 AND created_at > '2024-01-01'. Design index.
    Column order: equality first (user_id), then range (created_at)
  • L2
    Partial Index for Soft Delete
    drill · partial-index
    99% queries filter deleted=false. Create partial index on orders(user_id, created_at).
    WHERE deleted = false
  • L2
    Covering Index to Avoid Heap Fetch
    drill · covering-index
    Query: SELECT name, email FROM users WHERE status='active'. Create covering index.
    INCLUDE (name, email) or (status, name, email)
  • L2
    Fix Non-Sargable: YEAR(created_at) = 2024
    drill · sargability-fix
    WHERE YEAR(created_at) = 2024 never uses the index on created_at: the function call hides the column from the planner's cost model. Rewrite it as a sargable range so the planner can actually estimate and use the index.
    created_at >= '2024-01-01' AND created_at < '2025-01-01'
    An index on created_at becomes eligible for Index Scan / Bitmap scan once the column stands alone
  • L2
    Bitmap AND Reasoning
    drill · bitmap-scan
    Query: WHERE dept_id = 1 AND salary > 50000. There is no composite index, only single-column idx_emp_dept and idx_emp_salary. Justify why the planner combines both via BitmapAnd instead of committing to one index, and when you'd replace them with a composite index.
    Each index yields a bitmap; BitmapAnd intersects them in memory; the heap is fetched once
    Recheck Cond appears when bitmaps are lossy (page-level, not tuple-level)
    When both predicates are highly selective — or the query is hot — a composite (dept_id, salary) index wins
  • L2
    Expression Index for Annual Salary
    drill · expression-index
    Query: WHERE salary * 12 > 120000. Create functional index.
    CREATE INDEX ON employees ((salary * 12))
  • L2
    work_mem Hash Spill Predicament
    drill · hash-spill + work-mem
    A hash join with a ~2GB build side is orders of magnitude slower than expected. Read the EXPLAIN ANALYZE (it shows hash batches > 1, i.e., spill), then choose mitigations: what does raising work_mem do, and what query-level change could shrink the build side?
    EXPLAIN ANALYZE reports 'Hash Batches: 2' or more — the hash table exceeded work_mem and spilled to temp files
    Raise work_mem (per-operation memory) so the hash stays resident, or pre-filter rows so a smaller input feeds the hash
    The build side is chosen from row estimates — stale stats pick the wrong (bigger) build side

RE-READ BEFORE ANY INTERVIEW / CONTEST

  • Hash vs Nested-Loop: hash when both inputs are large but the hash fits in work_mem; nested loop when one side is small and the other is an indexed probe
  • Inner side: nested loop re-probes the inner for every outer row — put the smaller / cheapest input on the inside
  • work_mem: budget for sorts, hash tables, materialization; exceed it and the hash spills to disk (slow)
  • Covering index (INCLUDE): index-only scan holds the answer, no heap fetch
  • Stats freshness: ANALYZE keeps n_distinct, MCV lists, histograms current — stale stats → wrong cardinality → wrong join order
  • Merge join needs sorted inputs; the sort or an actually-sorted index must beat the hash+nested-loop alternatives

Glossary

cost modelPlanner's estimate of work (startup + per-tuple cost) for each plan node; drives join order and node choice.
hash joinBuild a hash table on one input, probe with the other. Memory-heavy; spills to disk if over work_mem.
nested-loop joinFor each outer row, probe the inner input. Best when the outer is small and the inner is an index probe.
merge joinBoth inputs sorted on the join key, then merged linearly. Requires sorted inputs or a sort.
work_memPer-operation memory budget for sorts, hash tables, and materialization. Exceeding it spills to disk.
spillWhen an operation exceeds work_mem and writes intermediate data to temp files — much slower than in-memory.
estimate / cardinalityRow-count predictions that statistics feed the planner; selectivity drives the cost model.
covering indexIndex whose key + INCLUDE payload holds every column a query needs — enabling index-only scans.
