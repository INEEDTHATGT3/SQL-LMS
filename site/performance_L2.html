Join Algorithms — How the Planner Joins

Planner picks algorithm: Nested Loop (small + index), Hash Join (large, no index), Merge Join (pre-sorted). EXPLAIN shows which. You can influence with indexes, stats, enable_* settings.
join algorithms in EXPLAIN
-- Nested Loop: outer rows × index probe
EXPLAIN SELECT * FROM small s JOIN big b ON s.id = b.sid;
-- Nested Loop (big has index on sid)

-- Hash Join: build hash on smaller, probe larger
EXPLAIN SELECT * FROM a JOIN b ON a.id = b.id;
-- Hash Join (no useful indexes, both large)

-- Merge Join: both sorted
EXPLAIN SELECT * FROM a JOIN b ON a.id = b.id;
-- Merge Join (both have indexes on id, or pre-sorted)

Hash Join: Build side (5000 rows) → hash table in memory. Probe side (10000 rows) → hash probe. If hash table > work_mem → spills to disk (slow). Increase work_mem for big joins.
Hash Join spills to disk when:
AHash table > work_mem
BTable > 1GB
CNo index on join key
DJoin is FULL OUTER
work_mem controls hash table memory. Spill = massive slowdown. Increase work_mem or use indexes.
Merge Join is chosen when:
ATables already sorted on join key
BIndexes exist on join key
CBoth tables have ORDER BY on join key
DAll of the above
Merge Join requires sorted input. Index scan or explicit sort provides ordering.

Statistics & ANALYZE — Teaching the Planner

How Planner Estimates Selectivity

Planner uses: histogram (most common values), n_distinct, null_frac, correlation. For range: histogram bounds + linear interpolation. For equality: MCV list + 1/n_distinct for non-MCV. For correlated columns: independence assumption (wrong) unless extended stats exist.

Bitmap Index Scan: Combines multiple indexes in memory (bitmap), then single heap fetch. Great for AND/OR combinations where no composite index exists. Recheck Cond means heap tuple rechecked (lossy pages).
Bitmap Index Scan is chosen when:

BMultiple indexes can be combined for AND/OR
CTable is tiny
DIndex is corrupted

Advanced Indexing — Partial, Expression, Concurrent

Partial Indexes — Index Only What You Query

partial index
-- 90% queries: WHERE status = 'active'
CREATE INDEX idx_emp_active ON employees (salary) WHERE status = 'active';

-- Size: fraction of full index
-- Query uses it:
SELECT * FROM employees WHERE status = 'active' AND salary > 50000;
-- Index Scan on idx_emp_active

-- Partial unique: one 'active' per email
CREATE UNIQUE INDEX idx_email_active ON users (email) WHERE status = 'active';
-- Allows 'alice@x.com' in 'inactive' + 'active'

Expression must be IMMUTABLE. No NOW(), random(), volatile functions. Expression index stores computed value — if function isn't immutable, index becomes inconsistent.

RE-READ BEFORE ANY INTERVIEW / CONTEST

  • Nested Loop: small outer + indexed inner; Hash: large both, build hash on smaller; Merge: pre-sorted
  • Composite index: equality first, then range; (a,b) works for a=1 and a=1,b=2
  • Partial index: WHERE clause on index — smaller, faster for skewed access
  • Covering index (INCLUDE): index-only scan, avoids heap fetch
  • Sargable: column naked on left, constant on right. No functions/math/casts on column
  • Bitmap Index Scan: combines multiple indexes in memory; Recheck Cond = lossy pages

Glossary

nested loop joinFor each outer row, probe inner index. Best: small outer + indexed inner.
hash joinBuild hash table on smaller input, probe with larger. Memory-heavy; spills to disk if > work_mem.
merge joinBoth inputs sorted on join key; linear merge. O(N+M). Requires sorted input.
partial indexIndex with WHERE clause — only indexes subset of rows matching condition.
covering indexIndex with INCLUDE columns — satisfies query without heap lookup.
sargableSearch ARGument ABLE — predicate that can use index seek (e.g., col = 5).
