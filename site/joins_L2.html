Join Algorithms — How the Planner Executes

Planner picks algorithm: Nested Loop (small + index), Hash Join (large, no index), Merge Join (pre-sorted). EXPLAIN shows which. You can influence with indexes, stats, enable_* settings.
join algorithms in EXPLAIN
-- Nested Loop: outer rows × index probe
EXPLAIN SELECT * FROM small s JOIN big b ON s.id = b.sid;
-- Nested Loop (big has index on sid)

-- Hash Join: build hash on smaller, probe larger
EXPLAIN SELECT * FROM a JOIN b ON a.id = b.id;
-- Hash Join (no useful indexes, both large)

-- Merge Join: both sorted
EXPLAIN SELECT * FROM a JOIN b ON a.id = b.id;
-- Merge Join (both have indexes on id, or pre-sorted)

Hash Join: Build side (5000 rows) → hash table in memory. Probe side (10000 rows) → hash probe. If hash table > work_mem → spills to disk (slow). Increase work_mem for big joins.
Hash Join spills to disk when:
AHash table > work_mem
BTable > 1GB
CNo index on join key
DJoin is FULL OUTER
work_mem controls hash table memory. Spill = massive slowdown. Increase work_mem or use indexes.
Merge Join is chosen when:
ATables already sorted on join key
BIndexes exist on join key
CBoth tables have ORDER BY on join key
DAll of the above
Merge Join requires sorted input. Index scan or explicit sort provides ordering.

LATERAL JOIN — Correlated Subquery in FROM

LATERAL — The Game Changer

lateral basics
-- For each employee, get their latest order
SELECT e.name, o.order_date, o.total
FROM employees e
LEFT JOIN LATERAL (
  SELECT * FROM orders o
  WHERE o.emp_id = e.id
  ORDER BY o.order_date DESC
  LIMIT 1
) o ON true;

-- Equivalent correlated subquery (harder to read)
SELECT e.name,
  (SELECT order_date FROM orders o WHERE o.emp_id = e.id ORDER BY order_date DESC LIMIT 1) AS latest_date,
  (SELECT total FROM orders o WHERE o.emp_id = e.id ORDER BY order_date DESC LIMIT 1) AS latest_total
FROM employees e;

Inside FROM, a LATERAL subquery can reference:
AOnly tables in same FROM
BColumns from LEFT side of join
COnly columns from same subquery
DGlobal variables only
In the join pipeline, the lateral side reads columns already produced by the LEFT side of the join — like a correlated subquery in FROM.
Compared with CROSS JOIN LATERAL, LEFT JOIN LATERAL:
ASame
BCROSS = inner (drops left rows with no match), LEFT = preserves left
CLEFT not allowed with LATERAL
DCROSS not allowed
In the pipeline, CROSS JOIN LATERAL = INNER JOIN LATERAL and drops left rows with no match; LEFT JOIN LATERAL preserves them (NULL if no match).

Semi/Anti Joins & Join Order

Semi-Join (EXISTS/IN) vs Anti-Join (NOT EXISTS/NOT IN)

semi/anti join patterns
-- Semi-join: EXISTS (stops at first match)
SELECT * FROM employees e
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.emp_id = e.id);
-- Returns employees WITH orders (no duplication)

-- Anti-join: NOT EXISTS
SELECT * FROM employees e
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.emp_id = e.id);
-- Employees with NO orders

-- IN semi-join (same logic)
SELECT * FROM employees WHERE id IN (SELECT emp_id FROM orders);

-- NOT IN anti-join (NULL trap!)
SELECT * FROM employees WHERE id NOT IN (SELECT emp_id FROM orders);
-- Watch for NULLs in subquery!

"Not In" + subquery with NULL = zero rows. Always use NOT EXISTS for anti-join. Or: WHERE id NOT IN (SELECT emp_id FROM orders WHERE emp_id IS NOT NULL).

60-second revision card

RE-READ BEFORE ANY INTERVIEW / CONTEST

  • Nested Loop: small outer + indexed inner; Hash: large both, build hash on smaller; Merge: pre-sorted
  • LATERAL: right side sees left columns; CROSS JOIN LATERAL = inner, LEFT JOIN LATERAL = outer
  • Semi-join (EXISTS/IN): left columns only, stops at first match; Anti-join (NOT EXISTS): no match
  • NOT IN + subquery with NULL = disaster; always NOT EXISTS for anti-join
  • Join order: planner decides; join_collapse_limit=1 forces written order; pg_hint_plan for hints
  • FULL JOIN = LEFT UNION RIGHT; MySQL 5.7 workaround: LEFT UNION RIGHT

Glossary

nested loop joinFor each outer row, probe inner index. Best: small outer + indexed inner.
hash joinBuild hash table on smaller input, probe with larger. Memory-heavy; spills to disk if > work_mem.
merge joinBoth inputs sorted on join key; linear merge. O(N+M). Requires sorted input.
lateral joinRight subquery references left columns. Like correlated subquery in FROM clause.
semi-joinEXISTS/IN pattern — returns left rows only, stops at first match per left row.
anti-joinNOT EXISTS pattern — returns left rows with NO match in right.
