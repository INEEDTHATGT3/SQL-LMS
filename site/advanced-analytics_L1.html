Metrics, Dimensions & Grain

A metric is a quantifiable number you aggregate (revenue, buyers). A dimension is the label you slice by (day, country). The grain is the unit of observation a result row is unique by — here, one row per (day, country). Deciding the grain before writing SQL is the decision every downstream table inherits: change the grain and every ratio in the report changes meaning.

daily revenue & buyers by country
SELECT order_date::date AS day,
       country,
       SUM(amount)            AS revenue,
       COUNT(DISTINCT user_id) AS buyers
FROM orders
GROUP BY order_date::date, country;

Conditional Aggregates — FILTER & CASE

FILTER (WHERE …) and CASE

conditional aggregates
-- Baseline: one row per status
SELECT status,
       COUNT(*)  AS n,
       SUM(amount) AS total
FROM orders
GROUP BY status;

-- FILTER: several conditional aggregates in a single scan, no GROUP BY needed
SELECT COUNT(*) FILTER (WHERE status = 'paid')   AS paid_orders,
       SUM(amount) FILTER (WHERE status = 'paid') AS paid_gmv,
       COUNT(*) FILTER (WHERE status = 'pending') AS pending_orders
FROM orders;

-- CASE equivalent: identical numbers, different spelling
SELECT COUNT(CASE WHEN status = 'paid' THEN 1 END)    AS paid_orders,
       SUM(CASE WHEN status = 'paid' THEN amount END) AS paid_gmv,
       COUNT(CASE WHEN status = 'pending' THEN 1 END) AS pending_orders
FROM orders;

MySQL 8.0 has no FILTER clause — reach for the CASE form (SUM(CASE WHEN status='paid' THEN amount END)) there. Both compute identical numbers; FILTER is the modern spelling and keeps the predicate next to the aggregate it decorates.
FILTER (WHERE status='paid') — which is true?
AIt removes rows from the result set
BIt applies only to the aggregate it decorates
CIt is a PostgreSQL-only join hint
DIt disables the WHERE clause
FILTER scopes a single aggregate to matching rows without altering the result set's other columns.
In SUM(CASE WHEN status='paid' THEN amount END), what does an unpaid order contribute?
A0
BNULL
CNegative amount
DIt drops the whole group
CASE returns NULL when no branch matches; SUM ignores NULLs, so unpaid orders add nothing while the row's other aggregates stay intact.

Cross-Tabs — CASE Pivot & crosstab()

CASE Pivot — Months as Columns

case pivot
SELECT region,
       SUM(CASE WHEN date_trunc('month', order_date) = DATE '2024-01-01' THEN amount END) AS m1,
       SUM(CASE WHEN date_trunc('month', order_date) = DATE '2024-02-01' THEN amount END) AS m2
FROM orders
GROUP BY region;

crosstab() version
CREATE EXTENSION IF NOT EXISTS tablefunc;

-- Two-argument crosstab: (row query, category query)
-- The category query's values become column names; you DECLARE their types below.
SELECT *
FROM crosstab('SELECT region, date_trunc(''month'', order_date)::date AS m, SUM(amount)
              FROM orders GROUP BY 1, 2 ORDER BY 1, 2',
              'SELECT DISTINCT date_trunc(''month'', order_date)::date AS m FROM orders ORDER BY 1')
     AS ct (region text, m1 numeric, m2 numeric);

Two-argument crosstab(row_sql, category_sql) pairs every row of the first query with a category list produced by the second. The output shape (AS ct (…)) is written by you — crosstab can't infer column names or types from the SQL strings. That manual declaration is exactly what makes dynamic pivots tricky (see L4).

Why must crosstab() output column types be declared explicitly?
ABecause column names must be quoted
BBecause the second query's values become column names with unknown types
CBecause crosstab is not a function
DStored procedures forbid it
The category values become output columns; PostgreSQL needs the explicit AS ct (...) column list with types.
The CASE pivot needs which clause to collapse many order rows into one row per region?
AWHERE
BGROUP BY region
CORDER BY
DDISTINCT ON
GROUP BY region condenses the raw rows; each SUM(CASE ...) fills one month column of that region's pivot row.

60-second revision card

RE-READ BEFORE ANY INTERVIEW / CONTEST

  • Grain = the unit of observation a result row is unique by (e.g. one row per (day, country)); pick it before writing SQL
  • COUNT(*) counts rows; COUNT(column) skips NULLs; COUNT(DISTINCT column) counts unique non-null values
  • FILTER (WHERE …) scopes one aggregate; CASE scopes one value — identical math, FILTER is the modern spelling
  • CASE pivot: one SUM(CASE …) per column inside GROUP BY; crosstab() rotates without hand-written expressions
  • crosstab() output columns must be declared in AS ct (…); the category query decides which columns exist

Glossary

grainThe unit of observation a result set is unique by — e.g. one row per (day, country).
metricA quantifiable number computed from rows (revenue, buyers, GMV).
dimensionA label used to slice or group rows (day, country, region).
cross-tabA pivot report rotating row-dimension values into columns; done with CASE aggregation or crosstab().
FILTER clauseAGG(expr) FILTER (WHERE cond) — a conditional aggregate that scopes only the aggregate it decorates.
additive metricA metric that sums correctly across grains (revenue); non-additive metrics (distinct buyers) need explicit re-aggregation per grain.
