Mental Model — Time as a First-Class Citizen

Querying time is not about WHERE clauses alone — it is about bucketing, framing, and filling. Think in intervals, not instants.

Every time-series problem decomposes into three moves: align timestamps to a common grid (bucketing), frame rows relative to each other (windows over time), and fill missing slots so the grid stays dense (gap filling). Geospatial adds a fourth move — proximity — which is just a WHERE clause that a spatial index can accelerate.

  • Bucketing: collapse timestamps into fixed intervals (hour, day, week)
  • Framing: LAG/LEAD/rolling frames over time-ordered rows
  • Filling: synthesize missing buckets so analysts see zeros, not gaps
  • Proximity: filter by distance using ST_DWithin before expensive ST_Distance

Gap Filling & Interpolation

Sparse data in, dense grid out

Sensors go down, dashboards hide zeros, joins lose matches. The fix is to generate the full calendar and left-join reality onto it. Analytics consumers expect one row per bucket — with zero counts, not missing rows.

fill empty buckets
-- Step 1: generate all hours for the window
WITH hours AS (
  SELECT generate_series(
    date_trunc('hour', now()) - INTERVAL '23 hours',
    date_trunc('hour', now()),
    INTERVAL '1 hour'
  ) AS hour_bucket
)
-- Step 2: left join real counts onto the grid
SELECT h.hour_bucket, COALESCE(c.events, 0) AS events
FROM hours h
LEFT JOIN (
  SELECT date_trunc('hour', ts) AS hour_bucket, COUNT(*) AS events
  FROM page_views
  WHERE ts >= now() - INTERVAL '24 hours'
  GROUP BY 1
) c ON c.hour_bucket = h.hour_bucket
ORDER BY h.hour_bucket;
# Python version pending — add after validation.
-- generate_series(x, y, INTERVAL '1 hour')
-- LEFT JOIN + COALESCE(..., 0) = dense grid
-- MySQL has no generate_series; build a numbers/tally table
SELECT DATE_ADD('2024-01-01', INTERVAL n DAY) AS d
FROM numbers_tally
WHERE n BETWEEN 0 AND 30;

Forward-fill (LOCF) & interpolation

last observation carried forward
-- LOCF: repeat the last known value across gaps
-- PostgreSQL 10+ supports IGNORE NULLS
SELECT
  ts,
  temp_c,
  COALESCE(
    temp_c,
    LAST_VALUE(temp_c IGNORE NULLS)
      OVER (ORDER BY ts ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
  ) AS temp_filled
FROM sensor_readings
ORDER BY ts;

-- Linear interpolation (simple two-probe version):
-- assign gaps to the mid-point between neighbors
# Python version pending — add after validation.
-- IGNORE NULLS is PostgreSQL 10+ syntax
-- For cross-dialect fill, join the probe grid to readings and use LAG
-- MySQL 8.0: no IGNORE NULLS; emulate with a correlated subquery
SELECT r.ts,
  COALESCE(r.temp_c, (
    SELECT rr.temp_c FROM sensor_readings rr
    WHERE rr.ts <= r.ts AND rr.temp_c IS NOT NULL
    ORDER BY rr.ts DESC LIMIT 1
  )) AS temp_filled
FROM sensor_readings r;

LOCF hides missingness. Always record is_filled (or a flag) alongside the fill so downstream models can distinguish observed values from imputed ones. A silent fill is a silent bug.
After LEFT JOIN to generated hours, missing hours appear with:
ANULL, unless COALESCE'd to 0
BA random token
CThe previous value
DAn error
Unmatched rows yield NULL for the aggregated column; COALESCE(events, 0) renders them as explicit zero.
WHY_HIDDEN: LOCF differs from linear interpolation because LOCF:
AChanges timestamps
BReuses the last observed value, not the arithmetic mean
COnly works on integers
DDeletes rows
LOCF copies the previous value forward; linear interpolation estimates between two neighbors. Choose by domain semantics.

Rolling Windows over Time

Moving averages on irregular clocks

rolling average
-- 7-point moving average (row-count frame)
SELECT
  ts,
  value,
  ROUND(AVG(value) OVER (
    ORDER BY ts ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
  ), 2) AS ma_7
FROM metrics
ORDER BY ts;

-- 24h moving average (time-based frame)
SELECT
  ts,
  value,
  ROUND(AVG(value) OVER (
    ORDER BY ts RANGE BETWEEN INTERVAL '1 day' PRECEDING AND CURRENT ROW
  ), 2) AS ma_24h
FROM metrics
ORDER BY ts;

-- Per-point delta and growth

Spatial Proximity — Distance, Buffers, Nearest

Distance in meters, not degrees

A lat/lon pair is stored as degrees (SRID 4326). Distance in degrees is meaningless for humans. Transform to a projected CRS — or use geography — before comparing meters.

distance & within
-- Distance between two points (projected, meters)
SELECT
  ST_Distance(
    ST_Transform(a.geom, 3857),
    ST_Transform(b.geom, 3857)
  ) AS meters
FROM places a, places b
WHERE a.id = 1 AND b.id = 2;

-- Pre-filter with DWithin (index-friendly), then refine
SELECT p.id, p.name
FROM pois p
WHERE ST_DWithin(
  p.geom::geography,
  ST_SetSRID(ST_MakePoint(-122.4194, 37.7749), 4326)::geography,
  1000
)
AND ST_Distance(p.geom::geography,
                ST_SetSRID(ST_MakePoint(-122.4194, 37.7749), 4326)::geography) < 1000;
# Python version pending — add after validation.
-- geography uses great-circle meters directly
-- ST_DWithin(geog, geog, meters) uses GiST index when present
-- ST_Distance_Sphere returns meters
SELECT id, name
FROM pois
WHERE ST_Distance_Sphere(geom,
  ST_GeomFromText('POINT(-122.4194 37.7749)', 4326)) < 1000;

Nearest neighbor without the killer sort

nearest k
-- Nearest 5, ordered by distance
SELECT id, name,
  ST_Distance(
    geom::geography,
    ST_SetSRID(ST_MakePoint(-122.4194, 37.7749), 4326)::geography
  ) AS meters
FROM pois
ORDER BY
  geom <-> ST_SetSRID(ST_MakePoint(-122.4194, 37.7749), 4326)
LIMIT 5;

-- <-> is the KNN operator: index-assisted, no full sort
# Python version pending — add after validation.
-- <-> requires a GiST index on geom
-- ORDER BY distance + LIMIT => early termination
-- MySQL: no KNN operator; ST_Distance_Sphere + LIMIT (full sort)
SELECT id, name,
  ST_Distance_Sphere(geom, ST_GeomFromText('POINT(-122.4194 37.7749)', 4326)) AS meters
FROM pois
ORDER BY meters
LIMIT 5;

AIt is more accurate
BIt can use a spatial index
CIt always returns meters
DIt avoids NULLs
ST_DWithin is a candidate for GiST/BRIN index acceleration; ST_Distance on every row is a sequential scan.
The <-> KNN operator avoids a full ORDER BY by:
ASampling rows
BWalking the GiST index in distance order
CCaching results
DUsing a hash index
The index returns rows in increasing distance; combined with LIMIT the planner stops early.

60-second revision card

RE-READ BEFORE ANY INTERVIEW / CONTEST

  • Bucketing: date_trunc('hour', ts) collapses timestamps; empty buckets vanish from GROUP BY.
  • Gap filling: generate_series drives a calendar grid; LEFT JOIN + COALESCE(...) restores zeros.
  • LOCF: LAST_VALUE(x IGNORE NULLS) OVER (ORDER BY ts) carries the last observation; flag imputed rows.
  • Rolling frames: ROWS counts physical rows, RANGE counts value distance — choose per semantics.
  • Proximity: ST_DWithin(geog, p, 1000) filtiers with the spatial index; ST_Distance measures.
  • KNN: pg <-> operator + GiST index = index-ordered walk; MySQL falls back to a full sort.

Glossary

date_truncPostgreSQL function returning the start of a time bucket (hour, day, month...).
generate_seriesSet-returning function that emits one row per step; used to build calendar grids for gap filling.
LOCFLast Observation Carried Forward — fills NULLs by repeating the most recent non-null value.
RANGE frameWindow frame defined by value distance (e.g., last 24h) rather than row count.
ST_DWithinSpatial predicate filtering geometries within a distance; index-friendly and cheaper than computing exact distance.
KNN operator (<->)PostgreSQL GiST operator ordering rows by distance, enabling LIMIT-truncated nearest searches.
