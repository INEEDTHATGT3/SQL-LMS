Extended Statistics — Correlated Columns

Planner assumes column independence. city='NYC' AND zip='10001' → estimates selectivity as product. But they're correlated! Extended statistics (CREATE STATISTICS) teaches planner the truth.
create statistics
-- Capture correlation between city and zip_code
CREATE STATISTICS st_city_zip (DEPENDENCIES) ON city, zip_code FROM users;
ANALYZE users;

-- Now planner knows city → zip_code dependency
EXPLAIN SELECT * FROM users WHERE city = 'NYC' AND zip_code = '10001';
-- Better row estimate, better plan

-- N-distinct for GROUP BY
CREATE STATISTICS st_dept_role (NDISTINCT) ON dept_id, role FROM employees;
ANALYZE employees;

Expression Indexes — Complex Expressions

Multi-Column Expression Indexes

expression index patterns
-- Concatenated search
CREATE INDEX idx_full_name ON users ((first_name || ' ' || last_name));
-- WHERE first_name || ' ' || last_name = 'John Doe'

-- JSONB path
CREATE INDEX idx_tags ON events USING GIN ((data->'tags'));
-- WHERE data->'tags' @> '["urgent"]'

-- Date math
CREATE INDEX idx_year_month ON events ((date_trunc('month', created_at)));
-- WHERE date_trunc('month', created_at) = '2024-01-01'

-- Math expression
CREATE INDEX idx_annual_sal ON employees ((salary * 12));
-- WHERE salary * 12 > 120000

-- Requires IMMUTABLE functions only

-- Double parentheses!

Expression must be IMMUTABLE. No NOW(), random(), volatile functions. Expression index stores computed value — if function isn't immutable, index becomes inconsistent.
Index on (date_trunc('month', created_at)) helps query:
AWHERE created_at >= '2024-01-01'
BWHERE date_trunc('month', created_at) = '2024-01-01'
CWHERE created_at > '2024-01-01'
DAll of the above
Expression index only matches queries using the exact same expression.
Why must expression index functions be IMMUTABLE?
APerformance
BIndex consistency — same input must always give same output
CStorage efficiency
DParallel query support
If function returns different values for same input, index entries become wrong.

Predicate Optimization — Planner Internals

How Planner Estimates Selectivity

Planner uses: histogram (most common values), n_distinct, null_frac, correlation. For range: histogram bounds + linear interpolation. For equality: MCV list + 1/n_distinct for non-MCV. For correlated columns: independence assumption (wrong) unless extended stats exist.

viewing statistics
-- View column statistics
SELECT * FROM pg_stats WHERE tablename = 'employees';

-- Key columns:
-- null_frac, avg_width, n_distinct, most_common_vals, most_common_freqs
-- histogram_bounds, correlation

-- Increase stats target for better estimates
ALTER TABLE employees ALTER COLUMN salary SET STATISTICS 1000;
ANALYZE employees;

Bitmap Index Scan: Combines multiple indexes in memory (bitmap), then single heap fetch. Great for AND/OR combinations where no composite index exists. Recheck Cond means heap tuple rechecked (lossy pages).
Bitmap Index Scan is chosen when:
ASingle index matches
BMultiple indexes can be combined for AND/OR
CTable is tiny
DIndex is corrupted
BitmapAnd/BitmapOr combines multiple index scans in memory before heap access.
"Recheck Cond" in Bitmap Heap Scan means:
AIndex is corrupted
BHeap tuple rechecked due to lossy bitmap pages
CPredicate pushed to storage
DStatistics outdated
Lossy bitmap pages store page-level, not tuple-level. Must recheck each tuple.
