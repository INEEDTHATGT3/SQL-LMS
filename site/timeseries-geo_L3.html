Mental Model — Cost, Not Cardinality

Beginner SQL optimizes query text; advanced SQL optimizes storage layout. Time-series is a storage problem first, a query problem second.

Append-only chronological data has a special shape: rows are written in near-time order and rarely updated. That single fact changes everything — BRIN beats B-tree for scans, partitions beat a single giant heap, and precomputed aggregates beat recomputation. Learn to think: *what does the storage already know about the time order?*

  • Time-ordered writes => block-level summaries make sense (BRIN)
  • Retention windows => partition pruning beats DELETE + VACUUM
  • Repeated analytics => materialize the heavy aggregation
  • Point lookups ('latest per id') => a different beast: b-tree / DISTINCT ON

Indexing Time-Series — BRIN vs B-Tree

Why B-tree is often the wrong default

A B-tree on ts gives fast point and range lookups but its leaf pages grow with every insert, and on a 10B-row table the tree is deep and cache-hostile. BRIN instead records, per 128-page block range, the min and max ts. For a range query the planner skips whole ranges with no match — reading only the ranges that intersect your window.

BRIN vs B-Tree
-- Block Range Index on append-only time column
CREATE INDEX events_ts_brin ON events
  USING brin (ts) WITH (pages_per_range = 128);

-- B-tree for comparison (point / eq / prefix lookups)
CREATE INDEX events_ts_btree ON events USING btree (ts);

-- Inspect sizes: BRIN is tens of KB on a 100 GB table
-- vs B-tree at tens of MB and climbing on every write
SELECT pg_relation_size('events_ts_brin')  AS brin_bytes,
       pg_relation_size('events_ts_btree') AS btree_bytes;

BRIN degrades if rows are inserted out of time order (backfilled history, imports, reindex). Reordering or partitioning per time chunk keeps block summaries honest.
BRIN indexes are most effective when:
ARows are randomly distributed by key
BRows arrive roughly time-ordered and are rarely updated
CThe table is small
DThe lookup key is a UUID
Block-range min/max summaries only help when similar keys cluster in the same blocks — true for append-ordered time data.
A BRIN scan skips a block range when:
AThe range is locked
BThe range's recorded min/max does not overlap the WHERE window
CThe range has no index entries
DThe range exceeds pages_per_range
Pruning is exactly that: the planner checks each range's min/max against the predicate and discards non-overlapping ranges.

Downsampling & Pre-aggregation at Scale

Rollup tables & continuous aggregates

hourly rollup materialized view
-- Materialized hourly rollup (12 months retention)
CREATE MATERIALIZED VIEW hourly_metric AS
SELECT date_trunc('hour', ts) AS hour_bucket,
       entity_id,
       COUNT(*)    AS n,
       SUM(value)  AS sum,
       MIN(value)  AS min,
       MAX(value)  AS max,
       AVG(value)  AS avg
FROM raw_metric
WHERE ts > now() - INTERVAL '12 months'
GROUP BY 1, 2;

-- Refresh per hour (incremental vs full rewrite — see note)
REFRESH MATERIALIZED VIEW CONCURRENTLY hourly_metric;

Pre-filter before you aggregate

two-stage filter
-- 1) Coarse window filter on a tiny index/column
-- 2) Precise predicate only inside the window
SELECT date_trunc('day', ts) AS day_bucket, AVG(value)
FROM events
WHERE ts >= now() - INTERVAL '90 days'
  AND ts <  now()             -- coarse
  AND value IS NOT NULL       -- precise
GROUP BY day_bucket;

Rule of thumb: materialize the summary the analyst asks for every week, not the one they ask for once. Rollups pay for themselves on the 2nd repeated query.
A rollup view storing COUNT/SUM/MIN/MAX per hour:
ACannot answer AVG per day
BCan answer AVG per day via SUM/COUNT aggregates
CLoses all ability to filter
DMust store raw rows too
SUM(SUM) / SUM(COUNT) reconstructs a weighted average — keeping sufficient statistics enables higher-level rollups.

Advanced Gap Filling & ASOF Joins

ASOF: attach the latest known state

ASOF join via DISTINCT ON
-- For each price tick, attach the latest rate at or before it
WITH prices AS (
  SELECT ts, price FROM trades
), rates AS (
  SELECT ts AS rate_ts, rate FROM fx_rates
)
SELECT DISTINCT ON (p.ts)
  p.ts, p.price,
  r.rate
FROM prices p
LEFT JOIN rates r ON r.rate_ts <= p.ts
ORDER BY p.ts, r.rate_ts DESC;
# Python version pending — add after validation.
-- DISTINCT ON picks the closest preceding rate row
-- PostgreSQL's classic ASOF; kysoh/join-expansion for big data
-- MySQL: correlated scalar subquery
SELECT p.ts, p.price,
  (SELECT r.rate FROM fx_rates r
   WHERE r.rate_ts <= p.ts ORDER BY r.rate_ts DESC LIMIT 1) AS rate
FROM trades p;

Interpolate: not just carry, estimate

linear interpolation
-- Linear interpolation between surrounding observations
-- (weighted split of the interval by time distance)
WITH filled AS (
  SELECT
    ts,
    value,
    LAG(value IGNORE NULLS)  OVER (ORDER BY ts) AS prev_val,
    LAG(ts     IGNORE NULLS)  OVER (ORDER BY ts) AS prev_ts,
    LEAD(value IGNORE NULLS) OVER (ORDER BY ts) AS next_val,
    LEAD(ts     IGNORE NULLS) OVER (ORDER BY ts) AS next_ts
  FROM measurements
)
SELECT
  ts,
  value,
  COALESCE(value,
    prev_val + (next_val - prev_val) *
      (EXTRACT(EPOCH FROM (ts - prev_ts)) /
       EXTRACT(EPOCH FROM (next_ts - prev_ts)))
  ) AS interp
FROM filled;

-- IGNORE NULLS lets LAG skip NULLs (PG 10+)
-- MySQL: fill via correlated subqueries to next/prev non-null

Interpolation assumes continuity; ASOF assumes 'latest state applies'. Pick by domain. Financial rates are usually ASOF; temperature is usually linear. Encoding the wrong assumption invalidates the model downstream.
merge_asof(direction='backward') is the pandas sibling of:
ARANGE window frame
BThe SQL ASOF join (latest on-or-before)
CLOCF on a single series
DA cross join
Both pair each A-row with the most recent B-row whose key is <=; pandas names it direction='backward'.
DISTINCT ON (p.ts) ... ORDER BY p.ts, r.rate_ts DESC picks:
AThe earliest rate row
BThe latest rate row at or before p.ts
CA random rate row
DThe largest value rate
DISTINCT ON keeps the first row per p.ts after ORDER BY sorts rates newest-first within the on-or-before set.

Dialect Mastery — Time-Series & Geospatial

SELECT date_trunc('hour', ts) AS h, COUNT(*) FROM events GROUP BY h;
PostgreSQL 
SELECT date_trunc('hour', ts) AS h, COUNT(*) FROM events GROUP BY h;
MySQL 
SELECT DATE_FORMAT(ts, '%Y-%m-%d %H:00:00') AS h, COUNT(*) FROM events GROUP BY h;
Python (pandas) 
df.set_index('ts').resample('1H').size().rename('count')

ANSI SQL 
-- nearest neighbor by distance (ANSI: full sort)
SELECT id FROM pois ORDER BY distance(point) LIMIT 5;
PostgreSQL 
SELECT id FROM pois ORDER BY geom <-> :p LIMIT 5; -- GiST KNN
MySQL 
SELECT id FROM pois ORDER BY ST_Distance_Sphere(geom, :p) LIMIT 5;
Python (pandas) 
# GeoPandas sindex.nearest
idx = pois.sindex.nearest(point, num_results=5)
pois.iloc[idx]
Python (SQLAlchemy) 
# sqlalchemy func.sqla_utils: direct ORDER BY expression or raw
func.st_distancesphere(Pois.geom, p)
Which dialect-family performs KNN via <-> (GiST)?
AMySQL only
BPostgreSQL only
CANSI standard
DSQL Server
The <-> operator is a PostGIS/PostgreSQL native — other engines need explicit distance-sorted plans.
MySQL's bucket label for an hour is made with:
Adate_trunc('hour', ts)
BDATE_FORMAT(ts, '%Y-%m-%d %H:00:00')
CHOUR(ts) || ':00'
DCAST(ts AS HOUR)
DATE_FORMAT renders a string bucket; it prevents index usage, so combine with a date range predicate for pruning.

RE-READ BEFORE ANY INTERVIEW / CONTEST

  • BRIN (block-range min/max) beats B-tree for scans on append-ordered time data; breaks on out-of-order inserts.
  • Storage layout decides query speed: partition by time, index per partition, keep columns narrow.
  • Rollups: materialize hourly from raw, monthly from hourly; carry COUNT/SUM/MIN/MAX so higher levels stay derivable.
  • ASOF = attach latest on-or-before state; DISTINCT ON in pg, correlated subquery in MySQL, merge_asof in pandas.
  • Interpolation vs ASOF is a domain decision — continuity vs 'latest state applies'.
  • Dialect gaps: date_trunc (pg) vs DATE_FORMAT (mysql) vs resample (pandas); KNN <-> is pg-only.
