Vacuum & Bloat — MVCC Garbage Collection

Plans are only half the story — storage layout decides the other half. Vacuum health, cache behavior, and index-only scans are where real PostgreSQL tuning lives.

MVCC: rows are never edited in place

PostgreSQL does not update a heap tuple in place. An UPDATE writes a brand-new row version and leaves the old one available to transactions that might still see it; once no transaction can, the old version is a dead tuple. Dead tuples waste space, slow sequential scans (more pages to visit), and bloat indexes. Autovacuum is the background janitor: it removes dead tuples, advances the visibility map, refreshes statistics, and prevents transaction-id wraparound. It wakes on a schedule (autovacuum_naptime) and triggers per table from dead-tuple counts and scale factors. You tune those knobs for churn — you never switch autovacuum off.

seeing vacuum pressure
-- Which tables carry the most dead tuples?
SELECT relname, n_live_tup, n_dead_tup
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

-- How often the background janitor wakes up
SHOW autovacuum_naptime;

-- One-off: reclaim free space + refresh stats + report
VACUUM (VERBOSE, ANALYZE) orders;

Buffer Cache & Read Amplification

shared_buffers and the cache-hit ratio

Every heap page and index page is 8KB of storage. Read amplification is how many pages a query must pull in to answer it: an index lookup walks root → branch → leaf → heap row, and a bad plan turns a handful of reads into millions. The first line of defense is shared_buffers — PostgreSQL's in-memory page cache. A hot table that already sits in shared_buffers costs nothing: a sequential scan of it is memory reads, not disk I/O. The number that matters is the cache hit ratio — pages served from memory over total pages read — not the scan type. Throwing a cold multi-GB scan at the cache evicts hot pages (their pg_buffercache usagecount drops), starving the workload that actually pays the bills.

inspecting the buffer pool
-- How big is the buffer pool?
SHOW shared_buffers;

-- How many pages of the orders heap are resident in memory right now?
SELECT count(*) AS resident_pages
FROM pg_buffercache
WHERE relfilenode = 'orders'::regclass;

-- Which relations dominate the cache, and how hot are they?
SELECT c.relname,
       count(*) AS pages,
       count(*) FILTER (WHERE b.isdirty) AS dirty,
       max(b.usagecount) AS hottest_usage
FROM pg_buffercache b
JOIN pg_class c ON c.relfilenode = b.relfilenode
GROUP BY 1
ORDER BY pages DESC
LIMIT 10;

Index-Only Scans & Covering Indexes

Index Only Scan — the visibility map decides

A plain btree index returns row pointers; fetching the actual row from the heap is the expensive tail. An Index Only Scan reverses that: if every column the query needs is IN the index (key columns + INCLUDE payload) AND the heap page is all-visible, PostgreSQL returns the index entry directly — Heap Fetches: 0. 'All-visible' is a per-page fact recorded in the visibility map, and only VACUUM/autovacuum marks pages all-visible. On pages still being touched — or not yet vacuumed — the planner must fetch the heap tuple to double-check visibility; EXPLAIN then shows Heap Fetches > 0 and the covering advantage quietly evaporates.

covering index
-- Key columns drive the scan; amount rides along as payload
CREATE INDEX idx_orders_status_ts
  ON orders (status, created_at) INCLUDE (amount);

-- All needed columns are in the index → eligible for Index Only Scan
EXPLAIN SELECT amount
FROM orders
WHERE status = 'paid' AND created_at > now() - interval '7 days';

Fillfactor & Reorganization

fillfactor — page headroom is a policy decision

The default heap fillfactor is 100: every new page is packed full. That is fine for append-only loads but painful for UPDATE-heavy tables — an updated row that no longer fits its page is relocated, splitting pages and damaging locality. fillfactor = 70 reserves 30% of each page so short updates stay in place. It is a trade: more pages per table and slightly longer scans, in exchange for far less physical churn. The setting only affects new pages — existing pages keep their old packing until a rewrite. Index pages already default to fillfactor 90 for the same reason: room to insert without splitting.

fillfactor & bloat measurement
-- Create-time: leave headroom up front
CREATE TABLE logs (
  log_id   BIGSERIAL,
  ts       TIMESTAMPTZ NOT NULL,
  payload  TEXT
) WITH (fillfactor = 70);

-- Existing table: applies to pages created from now on
ALTER TABLE orders SET (fillfactor = 70);

-- Measure before you rewrite: how much of the table is empty?
CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT free_percent FROM pgstattuple_approx('orders');

Stored Procedures & Functions — PL/pgSQL at Scale

Function vs Procedure — and SETOF returns

function & procedure
-- FUNCTION returns a value / table; used inside SQL
CREATE FUNCTION dept_stats(dept_id int)
RETURNS TABLE(department int, avg_sal numeric, cnt bigint)
LANGUAGE sql
STABLE AS $$
  SELECT dept_id, AVG(salary)::numeric, COUNT(*)
  FROM employees WHERE dept_id = dept_stats.dept_id

CREATE PROCEDURE monthly_archive(m_thru date)

Plan caching: the hidden performance lever

PL/pgSQL caches the *plan template* per statement/key. A one-size-fits-all plan stays cached for the session — great for uniform workloads, a trap for skewed values. Parameters matter: generic plans win when statistics say the same plan fits all inputs; custom plans win on skew.

cached vs custom plan
-- Generic plan reused for every call
PREPARE lookup(int) AS SELECT * FROM emp WHERE id = $1;
EXECUTE lookup(1);
-- after 5 calls, planner commits to a generic plan

-- Prepared inside PL/pgSQL: same idea, automatic
CREATE FUNCTION emp_lookup(eid int)
RETURNS emp LANGUAGE plpgsql STABLE AS $$
  -- first 5 calls use custom; then generic unless re-prepared
  SELECT * INTO r FROM emp WHERE id = eid;
  RETURN r;
$$
-- re-plan on: schema change, ANALYZE, plan invalidation

Cursors, transactions, and SECURITY DEFINER

cursor + transaction + definer
-- Streaming a large result set with a cursor
DECLARE cur CURSOR FOR
  SELECT id FROM payments WHERE settled_at IS NULL;
-- fetch in batches inside a procedure loop

-- Transactional work inside a procedure
CREATE PROCEDURE settle_batch() LANGUAGE plpgsql AS $$
BEGIN
  BEGIN
    UPDATE payments SET settled_at = now() WHERE id = cur_rec.id;
    COMMIT;  -- allowed only in PROCEDURE, not FUNCTION
  END;
END;
$$;

LANGUAGE plpgsql
SECURITY DEFINER SET search_path = public AS $$

Dialect Mastery — Vacuum & Storage

Same job, different vocabulary

PostgreSQL, MySQL 8.0 InnoDB, and SQL Server all reclaim dead storage eventually — the verbs differ. PostgreSQL: autovacuum on a tunable schedule plus explicit VACUUM, visibility maps, per-table tuning, pgstat views. MySQL: record-level purge runs inside InnoDB (purge threads), and you compact explicitly — OPTIMIZE TABLE rebuilds the table, information_schema.tables.data_free reports reclaimable bytes. SQL Server exposes a fill-factor knob (FILLFACTOR) as an index option to keep page headroom — the same idea as a low heap fillfactor. The vocabulary differs; the goal — compact storage so reads stay cheap — is shared.

ANSI SQL 
-- Storage hygiene: reclaim dead versions of rows
VACUUM ANALYZE orders;
PostgreSQL 
VACUUM (VERBOSE, ANALYZE) orders;
-- autovacuum does this on a tunable schedule;
-- pg_stat_user_tables.n_dead_tup + pgstattuple quantify the problem
MySQL 
-- No autovacuum concept: InnoDB purge threads reap old versions automatically.
ANALYZE TABLE orders;
OPTIMIZE TABLE orders;  -- rebuild, free space (see information_schema.tables.data_free)
Python (pandas) 
# Filter out deleted rows: df = df[df['deleted'].isna()]
ANSI SQL 
-- SQL Server: same knob, index option
CREATE INDEX i ON t (c) WITH (FILLFACTOR = 70);
PostgreSQL 
CREATE TABLE t (...) WITH (fillfactor = 70);
CREATE INDEX i ON t (c) WITH (fillfactor = 90); -- btree default is 90
MySQL 
-- InnoDB: no per-table fillfactor; OPTIMIZE TABLE repacks pages
Python (pandas) 
# pandas: rebuild the frame to re-compact

RE-READ BEFORE ANY INTERVIEW / CONTEST

  • Dead tuples: MVCC appends new row versions on UPDATE; autovacuum reclaims them — tune scale_factor/threshold for churn, never disable it
  • Index-Only Scan triad: covering columns in the index + visibility map marks the page all-visible → Heap Fetches: 0
  • fillfactor: leave page headroom (e.g. 70) so short UPDATEs stay in-page (HOT); setting affects only new pages

Glossary

MVCCMulti-version concurrency control: writers append new row versions instead of overwriting, so readers never block writers.
dead tupleOld row version no longer visible to any transaction; reclaimed by VACUUM/autovacuum.
bloatDead space in table or index pages from row churn that has not been reclaimed or repacked.
visibility mapPer-heap-page bits marking pages where every row version is visible to everyone — enables index-only scans and cheap VACUUM.
index-only scanAnswering a query from index entries alone; requires all needed columns in the index and all-visible heap pages (Heap Fetches: 0).
covering indexIndex whose key + INCLUDE payload holds every column a query needs, removing heap fetches.
fillfactorPer-table (and per-index) page fill policy; leaving headroom keeps UPDATEs in-page and reduces relocation.
cache-hit ratioFraction of page reads served from memory; the leading indicator for whether tuning should focus on caching or on reducing reads.
