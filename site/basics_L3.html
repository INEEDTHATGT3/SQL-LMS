An Index Scan is generally faster than Seq Scan because:
AIt reads fewer pages by jumping via B-tree
BIt sorts data automatically
CIt uses more CPU but less I/O
DIt only works on primary keys
B-tree index lets the database jump directly to matching rows instead of scanning all pages.
In EXPLAIN output, 'cost=0.29..42.15' means:
AStartup cost 0.29, total cost 42.15 (arbitrary units)
BTakes 0.29ms to start, 42.15ms total
CCost is 0.29 for index, 42.15 for table
DRows 0.29 to 42.15
Cost is planner's estimate in arbitrary units. First = startup, second = total.
Which index type supports range queries (>, <, BETWEEN) efficiently?
AHash index
BB-tree index
CGIN index
DBRIN index
B-tree maintains sorted order, enabling range scans. Hash only supports equality.
Partial index (WHERE clause on index) is useful when:
AYou always query the same subset (e.g., status='active')
BTable has fewer than 100 rows
CColumn has all unique values
DYou need full-text search
Partial index only indexes rows matching condition — smaller, faster for that subset.
Covering index (INCLUDE columns) avoids:
AIndex creation
BHeap lookups (table access)
CSort operations
DJoin operations
INCLUDE columns stored in index leaf — query satisfied from index alone, no heap fetch.

Query Plans Deep Dive — EXPLAIN ANALYZE

EXPLAIN shows the plan; EXPLAIN ANALYZE runs it and shows actuals. Compare estimated vs actual rows — divergence = stale stats or bad assumptions.
explain variants
-- Plan only (no execution)
EXPLAIN SELECT * FROM employees WHERE salary > 50000;

-- Execute + actual timings
EXPLAIN ANALYZE SELECT * FROM employees WHERE salary > 50000;

-- JSON format (machine-readable)
EXPLAIN (ANALYZE, FORMAT JSON) SELECT * FROM employees WHERE salary > 50000;

-- With buffers (I/O detail)
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM employees WHERE salary > 50000;

-- PostgreSQL specific options

-- MySQL

EXPLAIN FORMAT=JSON SELECT ...;

AIndex is missing
BStatistics are stale (run ANALYZE)
CQuery is too slow
DWrong join type

Buffers: shared hit=120 means:
A120 index pages read from disk
B120 pages found in shared memory (cache)
C120 rows returned
D120ms elapsed

Index Types & When to Use

B-tree (Default) — The Workhorse

btree usage
-- Created automatically for PRIMARY KEY, UNIQUE
-- Manual creation
CREATE INDEX idx_employees_salary ON employees (salary);

-- Composite (order matters!)
CREATE INDEX idx_emp_dept_salary ON employees (dept_id, salary);

-- Supports: =, <, >, <=, >=, BETWEEN, IN, LIKE 'prefix%'
-- Does NOT support: LIKE '%suffix', functions on column
# Python version pending — add after validation.
-- Partial index (PostgreSQL)
CREATE INDEX idx_active_emp ON employees (salary) WHERE status = 'active';

-- Covering index
CREATE INDEX idx_emp_salary_name ON employees (salary) INCLUDE (name);
-- Covering index (MySQL 8.0+)
CREATE INDEX idx_emp_salary_name ON employees (salary, name);
-- MySQL stores included cols in secondary index automatically
⏳ Python slot reserved (added after validation)

Hash Index — Equality Only

Hash indexes only support = comparisons. Faster for point lookups but no range scans. PostgreSQL: CREATE INDEX ... USING HASH. MySQL MEMORY engine uses hash by default.

Other Types (PostgreSQL)

  • GIN — Generalized Inverted Index: arrays, JSONB, full-text search, col @> '{"key": "val"}'
  • GiST — Generalized Search Tree: geometric data, tsvector, range types
  • BRIN — Block Range Index: huge tables with natural correlation (timestamps, auto-increment IDs). Tiny size, coarse granularity.
  • SP-GiST — Space-Partitioned GiST: non-balanced structures (quadtrees, prefix trees)
Which index supports col @> '{"a":1}' (JSONB containment)?
AB-tree
BHash
CGIN
DBRIN
GIN is designed for composite values with containment/overlap operators.
BRIN index is best for:
ASmall tables with random data
BHuge tables with correlated columns (time, ID)
CFull-text search
DPrimary keys
BRIN stores min/max per block range. Tiny (KB vs GB) but only works when physical order matches logical.

Index Pitfalls — When Indexes Don't Help

functions on columns kill indexes
-- BAD: function on column → Seq Scan
SELECT * FROM employees WHERE UPPER(name) = 'ALICE';

-- GOOD: functional index
CREATE INDEX idx_emp_upper_name ON employees (UPPER(name));
-- or store normalized
ALTER TABLE employees ADD COLUMN name_upper TEXT GENERATED ALWAYS AS (UPPER(name)) STORED;
CREATE INDEX idx_emp_name_upper ON employees (name_upper);
# Python version pending — add after validation.
-- Functional index (PostgreSQL)
CREATE INDEX idx_emp_upper_name ON employees (UPPER(name));
-- Functional index (MySQL 8.0+)
CREATE INDEX idx_emp_upper_name ON employees ((UPPER(name)));
⏳ Python slot reserved (added after validation)
leading wildcard kills index
-- BAD: leading % → Seq Scan
SELECT * FROM employees WHERE name LIKE '%son';

-- GOOD: trailing % uses B-tree
SELECT * FROM employees WHERE name LIKE 'J%';
# Python version pending — add after validation.
-- Trigram index for leading wildcard (pg_trgm extension)
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_emp_name_trgm ON employees USING GIN (name gin_trgm_ops);
-- Now LIKE '%son' uses index!
-- Fulltext index for text search
ALTER TABLE employees ADD FULLTEXT(name);
SELECT * FROM employees WHERE MATCH(name) AGAINST('son');

Low selectivity = planner ignores index. If query returns >5-10% of table, Seq Scan is often faster (sequential I/O vs random). Check reltuples vs rows in EXPLAIN.
WHERE UPPER(name) = 'ALICE' ignores index on name because:
AUPPER is not deterministic
BFunction on column prevents B-tree usage
CCase-insensitive collation needed
DIndex only stores lowercase
B-tree stores raw column values. Function transforms value → can't traverse tree. Fix: functional index.
Planner chooses Seq Scan over Index Scan when:
ATable has < 100 rows
BQuery returns large fraction of table (>5-10%)
CIndex is fragmented
DAll of the above
Random I/O (index) vs sequential I/O (scan). Threshold depends on settings (random_page_cost).

Glossary

covering indexIndex that includes all columns needed by query (INCLUDE), avoiding table lookup.
partial indexIndex with WHERE clause — only indexes subset of rows.
functional indexIndex on expression (e.g., UPPER(col)) — supports queries with functions.
selectivityFraction of rows matching condition. Low selectivity = few rows = index friendly.
heap fetchTable lookup after index finds row pointer. Covering index eliminates this.
random_page_costPlanner parameter: cost of random I/O vs sequential. Higher = prefer Seq Scan.
