Data Types & Casting

Type Families — the Engine Decides Comparisons

Every column has a type, and the type decides how values compare, sort, and aggregate. Numeric: int4/int8 are fixed-width and can overflow on big sums; numeric is arbitrary-precision and the safe choice for money and totals; float8/real are approximate binary floats. Character: text/varchar/char. Temporal: timestamp (no zone), timestamptz (zone-aware), interval. Logical: boolean. Mixing types triggers implicit casts the engine picks for you — working explicitly is the contract that removes surprise.

type behavior in PostgreSQL
-- Cast a text literal to a timestamp
SELECT '2024-01-15 10:30:00'::timestamp;

-- Integer division truncates in PostgreSQL
SELECT 7/2   AS int_division;      -- 3
SELECT 7.0/2 AS float_division;    -- 3.5

-- Binary floats are approximate
SELECT 0.1 + 0.2;                  -- 0.30000000000000004

NULL & Three-Valued Logic

NULL Means Unknown — and Unknown Participates in Logic

NULL is not zero and not the empty string — it is *unknown*. Any comparison with NULL evaluates to a third truth value: UNKNOWN. col = NULL is never TRUE, so it never matches; filter with IS NULL / IS NOT NULL. Aggregates mostly ignore NULLs, which is exactly why count(*) and count(col) can disagree.

equality vs IS NULL
-- This matches nothing: NULL = NULL is UNKNOWN, not TRUE
SELECT * FROM users WHERE email = NULL;

-- These are the correct filters
SELECT * FROM users WHERE email IS NULL;
SELECT * FROM users WHERE email IS NOT NULL;
# Python version pending — add after validation.
-- PostgreSQL-only null-safe equality:
SELECT 5 IS NOT DISTINCT FROM NULL;      -- false
SELECT NULL IS NOT DISTINCT FROM NULL;   -- true
-- MySQL uses the <=> null-safe equal operator instead:
SELECT NULL <=> NULL;  -- 1
SELECT 5 <=> NULL;     -- 0

-- Supply a fallback for NULL
SELECT COALESCE(NULL, 'default');   -- 'default'

-- NULLIF(a, b) returns NULL when a = b, otherwise a
SELECT NULLIF(5, 5), NULLIF(5, 6);  -- NULL, 5

transaction with savepoints
BEGIN;

INSERT INTO orders (user_id) VALUES (42);

SAVEPOINT p1;                            -- mark a safe point

UPDATE stock SET qty = qty - 1
WHERE  sku = 'TS1';                     -- unwanted or failed step

ROLLBACK TO p1;                         -- undo ONLY the update

COMMIT;                                 -- commit the remaining INSERT

-- SAVEPOINT / ROLLBACK TO / RELEASE are SQL-standard and fully
-- supported in PostgreSQL; a savepoint may overlap and nest
-- MySQL 8.0 supports SAVEPOINT and ROLLBACK TO SAVEPOINT inside
-- transactions started with START TRANSACTION
⏳ Python slot reserved (added after validation)
Atomicity: a transaction commits all of its statements or none. ROLLBACK TO p1 unwinds work performed after the savepoint *without* aborting the whole transaction, so the earlier INSERT can still commit. This is the tool for partial-recovery flows.
After ROLLBACK TO p1;, what state is the transaction in?
AAborted and closed — nothing can commit
BStatements after p1 are undone; the transaction stays open and COMMIT still works
CThe entire transaction is rolled back to BEGIN
DA brand-new transaction starts immediately
ROLLBACK TO returns to the savepoint, discarding later work, and the transaction remains usable.

Query Evaluation Order

Logical Order of Operations

logical processing order
-- SQL's documented logical order (a contract, not an execution plan)
--  1. FROM        build the row source(s)
--  2. WHERE       filter individual rows
--  3. GROUP BY    form groups
--  4. HAVING      filter groups (aggregates allowed)
--  5. SELECT      compute output expressions and aliases
--  6. ORDER BY    final ordering
--
-- Real engines optimize aggressively and may physically reorder;
-- the clause order above is the logical contract that defines what
-- each clause is allowed to reference.
# Python version pending — add after validation.
-- PostgreSQL's planner may reorder freely as long as the result matches
-- MySQL 8.0 honors the same logical contract
⏳ Python slot reserved (added after validation)
where vs having
SELECT dept, count(*) AS n
FROM   emp
WHERE  salary > 3000       -- filters rows BEFORE grouping
GROUP  BY dept
HAVING count(*) > 5       -- filters groups AFTER aggregation
ORDER  BY n DESC;
# Python version pending — add after validation.
-- WHERE cannot reference count(*); HAVING can
-- Same behavior in MySQL 8.0
⏳ Python slot reserved (added after validation)

WHERE runs before grouping and can never reference aggregates. HAVING runs after grouping and can. The same reasoning explains why a SELECT alias is invisible in WHERE (aliases are computed last) yet perfectly legal in ORDER BY.

Which clause may reference an aggregate such as count(*)?
AWHERE
BHAVING
CJOIN ... ON
DLIMIT
HAVING runs after grouping, so it can test aggregate values; WHERE sees only raw input rows.
WHERE filters rows before GroupAggregate PostgreSQL
GroupAggregate cost=0.29..42.15 rows=8 width=8
Filter: (count(*) > 5)
Seq Scan on emp as e cost=0..31.5 rows=2000 width=12
Filter: (salary > 3000)
Reading the plan: the Filter: (salary > 3000) sits on the Seq Scan — rows are discarded before any grouping — then GroupAggregate forms groups by dept and drops groups via its own Filter: (count(*) > 5). That is the WHERE-before-HAVING contract, visible in the tree.

Dialect Differences — Types & NULL

ANSI SQL 
SELECT CAST('2024-01-15' AS DATE);
SELECT CURRENT_DATE;
PostgreSQL 
SELECT '2024-01-15'::date;                -- :: cast
SELECT '2024-01-15 10:30:00'::timestamp;
SELECT 5 IS NOT DISTINCT FROM NULL;      -- false
MySQL 
SELECT CAST('2024-01-15' AS DATE);
SELECT CAST('10:30' AS TIME);
SELECT CONVERT('2024-01-15', DATE);      -- alias for CAST
SELECT 5 <=> NULL;                       -- 0 (null-safe equal)
Python (pandas) 
pd.to_datetime('2024-01-15')
Python (SQLAlchemy) 
sa.cast(col, sa.Date)
ANSI SQL 
-- NULL is UNKNOWN everywhere
SELECT * FROM t WHERE col IS NULL;
PostgreSQL 
SELECT NULL = NULL;    -- NULL (UNKNOWN)
SELECT NULL IS NULL;   -- true
-- NULLs sort LAST in ASC order by default
MySQL 
SELECT NULL <=> NULL;  -- 1 (null-safe)
SELECT '' IS NULL;     -- 0: empty string is a value, not NULL
-- NULLs sort FIRST in ASC order by default
Python (pandas) 
df[df['col'].isna()]
