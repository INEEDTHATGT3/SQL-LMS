GROUPING SETS / ROLLUP / CUBE

Sets, Hierarchies, and Every Combination

GROUPING SETS ((region, dept), (region), ()) asks for exactly the subtotal groupings you need, in one pass. ROLLUP (region, dept) is shorthand for a hierarchy — finest grain up to the grand total. CUBE (a, b) is every subset combination, margins included. In the output a collapsed dimension shows as NULL, and GROUPING(col) reports 1 exactly when col was rolled away — the only reliable way to tell a subtotal NULL from a real NULL.

grouping sets
SELECT region,
       dept,
       SUM(amount)       AS revenue,
       GROUPING(region)  AS r_bucket,
       GROUPING(dept)    AS d_bucket
FROM orders
GROUP BY GROUPING SETS ((region, dept), (region), ());

Share-of-Total & Period Deltas

Window Aggregates over Grouped Output

share + delta
SELECT day,
       SUM(amount) AS revenue,
       SUM(amount) / SUM(SUM(amount)) OVER () AS share_of_all,
       SUM(amount) - LAG(SUM(amount)) OVER (ORDER BY day) AS day_delta
FROM orders
GROUP BY day
ORDER BY day;

period over period %
SELECT day,
       SUM(amount) AS revenue,
       ROUND(100.0 * (SUM(amount) - LAG(SUM(amount)) OVER (ORDER BY day))
              / NULLIF(LAG(SUM(amount)) OVER (ORDER BY day), 0), 2) AS pct_delta
FROM orders
GROUP BY day
ORDER BY day;

A window function over a GROUP BY result partitions the aggregate output, not the raw rows. The double SUM — SUM(SUM(amount)) OVER () — re-sums the group totals, which is exactly the grand total of revenue. Never write SUM(amount) / SUM(amount); after grouping there is no scalar amount left, and a naive re-sum would collapse to 1.
Why is SUM(amount)/SUM(SUM(amount)) OVER () correct but SUM(amount)/SUM(amount) wrong?
AThe window needs the grouped aggregate, so you re-sum the aggregate output
BSUM(amount) is undefined after GROUP BY
CThe inner SUM ignores FILTER
DThe outer SUM must be a percentage
After GROUP BY, the window must sum the grouped totals — SUM(SUM(amount)) OVER () — not re-sum the same column, which would collapse each row to 1.
The share-of-total column uses OVER () with no frame or partition. What does it compute?
AA running total up to each day
BThe grand total across all days
CThe current row's revenue only
DThe average daily revenue
With no ORDER BY, the window frame is the whole grouped set, so the window SUM equals the grand total — the denominator every share needs.

Cohort Retention & Funnel Basics

Cohorts Key on First Activity

A cohort is a group of users sharing a first-activity date — their acquisition period. Retention asks: of the users acquired in period P, how many are still active in period P+n? The funnel counts, per user, how deep they got through an ordered step sequence (signup → cart → purchase) within a single path.

retention over time
WITH first_orders AS (
  SELECT user_id, MIN(order_date)::date AS first_day
  FROM orders
  GROUP BY user_id
)
SELECT f.first_day AS cohort,
       (o.order_date::date - f.first_day) AS days_since,
       COUNT(DISTINCT o.user_id) AS retained
FROM first_orders f
JOIN orders o ON o.user_id = f.user_id
GROUP BY 1, 2;

funnel by rank
WITH steps AS (
  SELECT user_id, event, ts,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY ts) AS step_rank
  FROM events
  WHERE event IN ('signup', 'cart', 'purchase')
)
SELECT event,
       COUNT(DISTINCT user_id) AS users
FROM steps
GROUP BY event
ORDER BY MIN(step_rank);

Why is cohort membership defined with MIN(order_date) per user?
ATo find the latest purchase
BFirst purchase date sets the cohort period the user is attributed to
CTo avoid NULLs in LAG
DBecause order_date is an index key
Cohorts key on first activity; MIN(order_date) per user IS their first-purchase date, and every later period is measured against it.
Why does the funnel rank events with per-user step_rank instead of comparing absolute timestamps across users?
ARank orders each user's own sequence, so step order is per-user
BTimestamps are never comparable
Cstep_rank stores the event time
DIt avoids a JOIN to sessions
ROW_NUMBER() PARTITION BY user_id sequences each user's own path; absolute clock times cannot tell a quick buyer from a multi-session window shopper.

EXPLAIN — ROLLUP HashAggregate

EXPLAIN — ROLLUP HashAggregate PostgreSQL
HashAggregate cost=55..130 rows=30 width=40
Seq Scan on orders cost=0..45 rows=1000 width=40

A single HashAggregate computes every requested grouping set in one pass over orders — rollup does not rescan the table per subtotal level. The planner may add a trailing Sort when the query demands an order (e.g. ORDER BY region NULLS LAST, dept NULLS LAST), which is why rollups keep one-pass cost but still pay a final sort for human-readable output.

How many passes over orders does a single ROLLUP normally need?
AOne per grouping level
BOne HashAggregate pass for all sets, plus maybe a final sort
CTwo: one to count, one to order
DOne per view in the FROM clause
GROUPING SETS/ROLLUP/CUBE execute as one aggregation pass; ordering is applied afterwards only when requested.
