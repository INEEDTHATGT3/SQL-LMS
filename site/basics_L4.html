Constraints Beyond PK

CHECK, UNIQUE, FK, DEFERRABLE, EXCLUDE

Beyond PRIMARY KEY, the database can enforce domain rules (CHECK), row uniqueness (UNIQUE), referential integrity (FOREIGN KEY), and even cross-row relationships (EXCLUDE on GiST). Each one makes a guarantee that application code inherits — a bad row simply cannot be written.

check, unique, fk (PostgreSQL)
CREATE TABLE products (
  id          int PRIMARY KEY,
  slug        text NOT NULL,
  price       numeric CHECK (price > 0),
  supplier_id int REFERENCES suppliers(id)
);

-- UNIQUE as a separate constraint, so it can be composite
ALTER TABLE products
  ADD CONSTRAINT uq_products_slug UNIQUE (slug);

fk actions and deferrable
-- CASCADE: deleting the parent deletes the children
CREATE TABLE orders (
  id      int PRIMARY KEY,
  user_id int REFERENCES users(id) ON DELETE CASCADE
);

-- SET NULL: deleting the parent blanks the reference instead
CREATE TABLE audit_logs (
  id      int PRIMARY KEY,
  user_id int REFERENCES users(id) ON DELETE SET NULL
);

-- DEFERRABLE: the FK check waits until COMMIT, not statement end
CREATE TABLE bookings (
  id         int PRIMARY KEY,
  session_id int REFERENCES sessions(id)
              DEFERRABLE INITIALLY DEFERRED

exclusion constraints (EXCLUDE USING gist)
CREATE EXTENSION IF NOT EXISTS btree_gist;  -- needed for = on room_id

CREATE TABLE reservations (
  room_id int NOT NULL,
  slot_tsrange tsrange NOT NULL,
  EXCLUDE USING gist (
    room_id WITH =,
    slot_tsrange WITH &&
  )

A DEFERRABLE INITIALLY DEFERRED foreign key is enforced:
AAfter every statement, immediately
BOnly when the parent table is locked
CAt COMMIT, not at statement end
DNever, unless manually re-enabled
Deferrable constraints delay the check to the end of the transaction, so insertion order inside a transaction no longer matters.
Which constraint can compare data across different rows?
ACHECK
BNOT NULL
CEXCLUDE (GiST)
DDEFAULT

Normalization & Denormalization

1NF → 2NF → 3NF, then a Deliberate Denormalization Step

Normalization removes redundancy by splitting tables until each fact lives in exactly one place. 1NF: atomic values, no repeating groups. 2NF: no partial dependencies — a column must describe the whole key, not just part of it. 3NF: no transitive dependencies — a non-key column's only dependency is the key. Denormalization is the deliberate inverse: folding tables back together on read-hot reporting paths (star schemas with fact + dimension tables), trading write-side elegance for fewer joins at query time.

  supplier_name text
);

-- whole key (order_id, product_id) — a partial dependency, the 2NF
-- violation. The repeating block belongs in a child table.

the normalized split
CREATE TABLE suppliers (
  id   int PRIMARY KEY,
  name text NOT NULL

CREATE TABLE products (
  id          int PRIMARY KEY,
  name        text NOT NULL,
  price       numeric CHECK (price > 0),
  supplier_id int NOT NULL REFERENCES suppliers(id)

Views & Row-Level Security

Views are Stored Queries; RLS is Per-Row Filtering

a simple view
CREATE VIEW active_subscriptions AS
SELECT s.*
FROM   subscriptions s
WHERE  s.status = 'active';

-- Queries against the view behave as if against a filtered table
SELECT count(*) FROM active_subscriptions;
# Python version pending — add after validation.
-- A view is a named query; simple single-table views are
-- flattened into the outer query by the planner
-- MySQL views behave the same; simple views are inlined
⏳ Python slot reserved (added after validation)
security_invoker (PostgreSQL 15+)
-- By default a view runs with its OWNER's privileges, which can
-- leak rows the caller could not read directly.
-- security_invoker re-checks the calling user at every access:
CREATE VIEW v_customers
WITH (security_invoker = true) AS
SELECT * FROM customers;
# Python version pending — add after validation.
-- Without security_invoker, a user granted SELECT on the view may
-- see rows they cannot read from the base table directly
-- MySQL views execute with the DEFINER's privileges; there is no
-- SECURITY INVOKER option. Separate per-tenant views are the usual
-- workaround
⏳ Python slot reserved (added after validation)
row-level security policy
CREATE POLICY tenant_isolation ON customers
  FOR SELECT
  USING (tenant_id = current_setting('app.tenant_id')::int);

ALTER TABLE customers ENABLE ROW LEVEL SECURITY;

-- FORCE applies the policy even to the table owner
ALTER TABLE customers FORCE ROW LEVEL SECURITY;
# Python version pending — add after validation.
-- current_setting('app.tenant_id')::int reads a session GUC set
-- per request, e.g. SET app.tenant_id = 7;
-- MySQL 8.0 has no row-level security; emulate with per-tenant
-- views or app-level filters
⏳ Python slot reserved (added after validation)
RLS filters rows — it does not grant table access. If the user cannot reach the table at all, policies never run. The two checks layer: privileges (can you touch the table?) then policies (which rows may you see?).
A query against a simple single-table view usually shows the base table directly in the plan because…
Aviews are always materialized
Bthe planner flattens simple views into the outer query
Cthe view owns its own storage
DMySQL forces inlining in every case
Simple views are rewritten into the consuming query; only complex views (aggregates, DISTINCT, some joins) keep a Subquery Scan node.

EXPLAIN — Constraint & View Plans

The plan is where integrity meets the optimizer. A CHECK constraint can act as a guaranteed pre-condition during scans (and enables constraint exclusion on partitioned or inherited tables), and simple views vanish into the query that uses them.

CHECK constraint as a scan filter PostgreSQL
Seq Scan on products cost=0..22.5 rows=45 width=16
Filter: (price > 0)
Constraints are pre-conditions the planner can exploit. The Filter: (price > 0) reflects the guaranteed CHECK; on partitioned or inherited tables, constraint exclusion lets the planner skip entire children whose CHECK contradicts the query qualifier.
Aggregate over a view — the view is inlined PostgreSQL
GroupAggregate cost=0.29..38.4 rows=2 width=8
Seq Scan on subscriptions cost=0..18.2 rows=120 width=8
Filter: (status = 'active')
Simple views flatten. The plan references subscriptions directly, with the view's WHERE surfacing as a scan filter — no Subquery Scan node. Only complex views (aggregates, DISTINCT, some joins) can stay as Subquery Scan; an aggregate over a base view appears as GroupAggregate here because the view itself inlined.
The plan for SELECT status, count(*) FROM active_subscriptions GROUP BY status shows GroupAggregate over Seq Scan on subscriptions. Why is there no Subquery Scan node?
AThe view was flattened into the outer query
BViews are always materialized as tables
CGroupAggregate hides the view from the plan
DMySQL never shows Subquery Scan nodes
Simple views are inlined by the planner; only complex views keep a Subquery Scan node.

60-second revision card

RE-READ BEFORE ANY INTERVIEW / CONTEST

  • EXCLUDE (GiST) bans cross-row patterns (range overlap); CHECK cannot see other rows
  • DEFERRABLE INITIALLY DEFERRED moves FK checks from statement end to COMMIT
  • 1NF atomic + no repeating groups; 2NF no partial dependencies; 3NF no transitive dependencies; denormalize deliberately on read-hot facts
  • Simple views flatten into the outer query; security_invoker re-checks the caller; RLS filters rows and needs FORCE to cover the owner
  • ON DELETE CASCADE / SET NULL decide what happens to children when a parent disappears
  • Constraints are pre-conditions the planner exploits — filter lines, contradiction detection, constraint exclusion

Glossary

constraintA rule the database enforces (NOT NULL, UNIQUE, CHECK, FK, EXCLUDE) so that invalid rows cannot be written.
exclusion constraintA GiST-based constraint that rejects a new row overlapping an existing row (e.g., range intersections).
deferrable constraintA constraint whose check is postponed from statement end to transaction COMMIT.
normalizationRemoving redundancy through 1NF/2NF/3NF decompositions so each fact lives in one place.
denormalizationDeliberately re-joining tables (fact + dimension stars) to cut joins on read-heavy reporting paths.
row-level securityPer-row filtering enforced by policies keyed to the current user or session context.
security_invokerView option (PG 15+) that evaluates the calling user's privileges instead of the view owner's.
partial dependencyA column that depends on only part of a composite key — the 2NF violation.
