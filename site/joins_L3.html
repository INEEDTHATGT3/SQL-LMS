Join Elimination — When the Planner Skips the Join

Join elimination = free performance. If child has FK to parent PK, and you only select parent PK/FK columns, planner skips parent table entirely. The FK IS the data.
join elimination example
-- Schema: employees.dept_id → departments.id (FK)
-- Query only needs dept_id (already in employees!)
SELECT dept_id FROM employees;
-- Planner: no join needed! Seq Scan on employees only.

-- But adding department name kills elimination
SELECT e.dept_id, d.name
FROM employees e
JOIN departments d ON e.dept_id = d.id;
-- Now join required

-- LEFT JOIN also blocks elimination (might need NULL check)
SELECT e.dept_id FROM employees e LEFT JOIN departments d ON ...;

Predicate Pushdown — Filter Early, Join Less

Pushdown Through Views, CTEs, Subqueries

predicate pushdown
-- View with filter
CREATE VIEW active_employees AS
SELECT * FROM employees WHERE status = 'active';

-- Query with additional filter
SELECT * FROM active_employees WHERE dept_id = 3;
-- Planner pushes dept_id=3 INTO view scan
-- Single scan: status='active' AND dept_id=3

-- CTE pushdown
WITH active AS (SELECT * FROM employees WHERE status = 'active')
SELECT * FROM active WHERE dept_id = 3;
-- Same pushdown

-- Subquery pushdown
SELECT * FROM (SELECT * FROM employees WHERE status = 'active') e
WHERE dept_id = 3;
-- Pushdown works
# Python version pending — add after validation.
-- Pushdown automatic in PostgreSQL
-- Can be blocked by: VOLATILE functions, LIMIT/OFFSET in subquery, set operations
-- MySQL 8.0+: predicate pushdown improved
-- Derived table pushdown (merged)
⏳ Python slot reserved (added after validation)
Pushdown blockers: VOLATILE functions (random(), now()), LIMIT/OFFSET in subquery, UNION/EXCEPT, window functions in subquery, set operations. Use CTEs carefully.
Predicate pushdown shrinks the rows entering a join by moving the filter:
AFrom outer query INTO inner subquery/CTE
BFrom inner TO outer
CTo application layer
DTo storage engine only
Pushing the predicate into the inner subquery/CTE filters rows at the source, so fewer rows enter the join — cheaper probe/build.
A LIMIT inside a CTE is a pushdown boundary because:
ALIMIT changes semantics if pushed
BCTEs are optimization fences
CBoth A and B
DCTEs don't support pushdown
In PostgreSQL, CTEs are optimization fences (materialized). LIMIT inside CTE prevents pushdown.

Partition-Wise Join — Parallel Join at Scale

Partition-Wise Join

partition-wise join
-- Both tables partitioned on same key (e.g., event_time)
CREATE TABLE events_2024 PARTITION OF events FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
CREATE TABLE orders_2024 PARTITION OF orders FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

-- Join on partition key
SELECT * FROM events e JOIN orders o ON e.user_id = o.user_id;
-- Planner: partition-wise join
-- Each partition joins independently (parallel!)

-- Enable (default on in PG 11+)
SET enable_partitionwise_join = on;
SET enable_partitionwise_aggregate = on;

Each partition joins independently → massive parallelism. 12 monthly partitions = 12 parallel joins. Linear scale-out for time-series data. enable_partitionwise_aggregate pushes GROUP BY into partitions too.
Partition-wise join requires:
ASame partition key on both tables
BSame partition bounds
CBoth A and B
DDifferent partition keys
Both tables must be partitioned identically on the join key. Each partition pair joins independently.
enable_partitionwise_aggregate pushes:
AGROUP BY into partitions
BORDER BY into partitions
CLIMIT into partitions
DWHERE into partitions
Aggregate in each partition, then combine. Massive parallel GROUP BY.
